## 1. 原则

作品集不以“做了一个 AI App”为主线，而以一系列有证据的产品决策为主线：

```text
发现问题
→ 检查替代方案
→ 淘汰低价值方向
→ 定义可验证范围
→ 设计 AI 与规则边界
→ 建立评测
→ 上线 MVP
→ 用真实反馈迭代
```

## 2. 能力与证据映射

| AI 产品经理能力 | 项目中要产生的证据 | 最终展示方式 |
|---|---|---|
| 机会识别 | 真实经历访谈、替代方案分析、问题严重度 | 问题背景和用户旅程 |
| 产品判断 | 停止 UniCite、缩小首发场景 | 决策时间线 |
| 用户研究 | 研究计划、访谈综合、反证 | 洞察卡片和机会点 |
| MVP 取舍 | P0/P1/不做清单 | 范围对比图 |
| AI 工作流设计 | AI/规则引擎职责、人工控制点 | 系统流程图 |
| 评测能力 | 固定评测集、质量门槛、失败分类 | 版本对比表 |
| 指标设计 | 用户结果、模型指标、护栏指标 | 指标树或仪表板 |
| 风险治理 | 隐私、公平、降级、发布门槛 | 风险与缓解矩阵 |
| 跨职能沟通 | PRD、Schema、技术验证计划 | 文档节选 |
| 迭代能力 | 测试问题、修改记录、回归结果 | Before/After |
| 交付能力 | Demo、GitHub、部署、README | 可访问链接 |

## 3. 必须保留的过程材料

- 每次用户访谈的匿名记录；
- 研究综合中的反证；
- 重要范围变化；
- 规则版本和 Prompt 版本；
- 评测原始结果；
- 失败案例；
- 用户测试录像或观察记录（经授权）；
- 指标未达到时的处理；
- 发布前检查表；
- 最终已知限制。

## 4. Case Study 建议结构

1. 项目一句话与个人角色；
2. 为什么放弃前一个方向；
3. 多人共同决策中的真实问题；
4. 现有替代方案与机会；
5. 首发场景和 MVP 取舍；
6. AI 为什么需要、为什么不能直接决定；
7. 约束引擎与解释系统；
8. 评测集和失败分类；
9. 产品体验；
10. 用户测试与迭代；
11. 最终结果与限制；
12. 反思和下一步。

## 5. 最终量化结果候选

只有取得真实数据后才能选用：

- 决策任务完成率；
- 相比群聊基线减少的协调时间；
- 减少的追问次数；
- 硬性约束识别准确率；
- 推荐解释一致性；
- 用户对“必要条件被考虑”的评分；
- 修订后可接受方案形成率；
- 产品部署和测试覆盖情况。

禁止把目标值写成已实现结果。

## 6. 简历描述占位结构

最终项目描述建议遵循：

```text
通过[研究方法]识别[用户问题]，定义[聚焦场景与MVP]；
设计[AI工作流、规则引擎与人工控制点]，并用[评测规模与指标]验证；
上线[可运行产品]，在[用户测试规模]中取得[真实结果]，根据[发现]完成[关键迭代]。
```

当前没有真实结果，因此暂不生成最终简历 bullet。

## 7. 作品集发布门槛

- 每个关键结论可追溯到研究、测试或日志；
- 明确区分个人判断与用户证据；
- 至少展示一个失败或回退案例；
- 不隐去未达到的指标；
- Demo 和 GitHub 可以被招聘者独立验证；
- 不公开真实参与者的敏感信息；
- 所有数字能找到原始记录。
