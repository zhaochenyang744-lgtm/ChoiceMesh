## 1. 样本与证据限制

- 样本数少于计划，不能以“2/2”替代原计划的成功阈值。
- HF-01 对手机流程的描述明确为基于响应式代码推断，不是独立的真实手机操作证据。
- 两份记录均为文字过程记录，未提供完整耗时、屏幕录制或统一设备信息。
- 因此，本轮结果是定向证据：用于决定下一轮需验证什么，而非证明原型已经通过高保真测试。

## 2. 已获得支持的核心机制

| 机制 | 直接证据 | 结论 |
|---|---|---|
| 本人确认边界 | 两位均说明只有本人可核实交通或声明无法参加；提醒不改变他人状态。 | 暂未发现“可替他人确认”的误解。 |
| 匿名隐私边界 | 两位都能说明路线、私人原因、个人预算、预计确认具体时间不会进入共同页面。 | 隐私承诺能被理解，且提高如实填写意愿。 |
| 暂定与发布 | 两位均把正式决定定位在勾选确认并点击 Publish，而非 provisional selection。 | 两步承诺机制有效。 |
| 发布后版本保留 | 两位均理解调整或重新比较会开启新协调，而不撤销旧版本。 | 版本保留逻辑清楚。 |
| 候选比较 | 两位都能解释 C / A / B 的可行性与覆盖表列头。 | 本轮新增列头解决了原有的表格归属问题。 |

## 3. 问题清单与优先级

| 优先级 | 问题 | 证据 | 建议 |
|---|---|---|---|
| P1 | 测试入口与题设不一致。参与者先经过创建房间与邀请弹窗，才进入“已有协作状态”的 T1。 | HF-01 先创建后理解状态；HF-02 明确指出其不属于测试情境。 | 为测试提供独立的“协作中房间”深链接或测试启动按钮，直接落在 Now 状态。 |
| P1 | 默认“需要更多时间”日期过期，削弱情境可信度。 | HF-02 指出默认 8 月 8 日已早于测试情境。 | 用相对时间（如 Tomorrow, 6:00 PM）或按当前日期动态生成默认值。 |
| P2 | 移动端缺少流程位置感。 | HF-01 认为隐藏 flow steps 后容易“迷路”；HF-02 认为纯图标菜单对首次使用者偏弱。 | 在手机顶部保留当前步骤与下一步的简短进度提示；用真实手机操作再验证。 |
| P2 | `Needs verification` 的责任归属仍可能含糊。 | HF-02 不确定它指自己、另一位成员还是候选本身。 | 对个人行动统一使用 `Your verification needed` + 蓝色；对其他待核实保留琥珀色，并在卡片中写清“another member”。 |
| P2 | `boundary risk` 的决策含义仍需补充。 | HF-02 理解无需跟进，但不清楚它对决策意味着什么。 | 在首次出现处补一行简释：`Still viable, with no buffer. Publishing is allowed.` |
| P2 | `Select provisionally` 仍可能被误读为已经定案。 | HF-01 在到发布页后才理解 provisional 不通知成员。 | 暂定后的卡片直接显示 `Not notified yet — continue to Publish check.` |
| P3 | “75% response progress”可能被看成总体准备度而非回复率。 | HF-01 认为 3/4 已回复但仍有待核实，进度显得“虚高”。 | 将该指标明确命名为 `Responses received`，与行动待办分离，不呈现为决策完成率。 |
| P3 | `Prototype controls`干扰正式产品感。 | HF-01 不确定是否应点击该组测试按钮。 | 测试版本由主持人快捷键或独立控制面板推进；参与者版本不显示该组控件。 |

## 4. 本轮不构成问题的项目

- 两位均认为 Toast、弹窗与发布横幅对操作干扰有限；但没有统一的真实设备与时间证据，继续保留观察。
- 两位均愿意填写待核实或无法参加；前提是私人原因与具体数值不被公开。
- 两位均认为发布页的明确确认动作合适，应保留。

## 5. 设计决策

本轮不再继续细调高保真视觉。下一步先完成最小测试环境修订，再做一轮定向回测：

1. 增加直达“协作中”状态的测试入口；
2. 让“更多时间”使用动态或相对日期；
3. 手机端增加简洁的当前步骤 / 下一步提示；
4. 完成 `Needs verification`、边界风险与 provisional 的微文案修订；
5. 移除参与者可见的 `Prototype controls`，改由主持人推进状态。

该定向回测建议至少招募 3 位真实手机参与者。若资源不足，应明确把本轮高保真测试标记为“方向性研究”，而非最终验证。
