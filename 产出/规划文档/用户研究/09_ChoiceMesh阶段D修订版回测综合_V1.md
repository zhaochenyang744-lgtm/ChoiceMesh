## 1. 回测结论

修订后，“待核实”“边界风险”与“最终确认”均被两位参与者正确理解：待核实不等于确认，需由成员本人完成；边界风险是已验证但无余量，不阻止发布且会被保留；最终确认明确表达从“考虑中”转为正式结果。

阶段 D 达到进入 MVP 流程定义的门槛，但并不代表所有交互已定稿。下一阶段必须把三类状态和行动归属实现为一致的产品状态，而不能只停留在说明文案中。

## 2. 已验证的修订

| 修订目标 | 回测结果 |
|---|---|
| 待核实与边界风险分开说明 | 两位参与者均能复述：前者是未验证，后者是已验证但没有余量。 |
| 发起人不替成员确认 | 被理解为“成员本人核实，发起人记录已收到的确认”。 |
| 边界风险是否阻断发布 | 被正确理解为不阻断发布、也不会因确认而消失。 |
| 最终确认节点 | 勾选后才发布的机制被理解为正式承诺，而非群聊中的随口同意。 |

## 3. 未闭环的交互问题

| 问题 | 证据 | MVP 处理要求 |
|---|---|---|
| 等待回复状态未充分可见 | D-V2-01 在完整流程中找不到“尚未打开或未提交反馈”的独立状态 | 将回复进度单列为 `等待回复 / 已反馈`，不得并入条件待核实。 |
| 待核实与边界风险视觉接近 | D-V2-01 认为两者同为琥珀色，需读说明才能区分 | 在 MVP 使用不同色相和不同图形：待核实为蓝色实线，边界风险为琥珀色虚线，并配合文字。 |
| 比较页的行动归属不够直接 | D-V2-02 建议直接显示“谁处理 / 下一步是什么” | 每个候选显示聚合回复进度与下一步责任，例如“成员 2 核实交通”。 |
| 分支操作缺少可见结果 | D-V2-01 预期暂定、改选、接受缺席会改变状态 | 每项发起人操作必须改变房间状态、记录时间和可撤销范围。 |
| 发布后的问题回流未展示 | D-V2-01 询问“仍有问题”后由谁处理 | 成员可提交新问题；状态回到协调中，由发起人重新比较 / 暂定 / 发布。 |
| 最终确认措辞仍可更有行动感 | D-V2-01 建议从“我知道”改为“我确认” | 原型已修订为“我确认”；MVP 继续测试其压力与可接受度。 |

## 4. MVP 流程决策

MVP 采用两条并行状态，而非一个混合状态：

1. **成员回复状态**：等待回复 → 已反馈 → 已确认 / 无法参加。
2. **条件状态**：待核实 → 已验证；已验证条件可标记为边界风险或偏好让步。

发起人可以发出私密提醒、暂定方案、改选候选和按参与规则接受缺席；但不能代表成员填写或确认。发布后保留风险和让步，并允许成员将活动送回“协调中”。

## 5. 研究阶段结论

阶段 A–D 已完成：在线民族志、6 场真实经历访谈、群聊基线任务、首轮 3 人概念测试与修订版 2 人回测，共形成 5 份阶段 D 测试反馈。研究支持继续进入 MVP 流程与需求定义，前提是保持“已有候选、AI 整理解释、人类确认发布、默认不公开个人理由”的产品边界。
