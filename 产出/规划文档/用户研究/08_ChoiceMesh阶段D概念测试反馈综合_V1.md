| 字段 | 内容 |
|---|---|

| 样本 | 3 名参与者（D01–D03） |

| 证据边界 | 小样本概念测试，用于发现理解与流程风险，不用于估计比例或确认需求规模 |

## 1. 结论

本轮最强的正向信号是：三位参与者均理解并认可“最终确认是明确动作，而不是群聊中的隐性共识”。日常语言版的条件表达、隐私保护与保留让步的结果呈现也获得一致正向反馈。

最大的流程问题不在“是否需要更多说明”，而在状态模型必须更清楚：成员是否已回复、条件是否已核实、条件是否存在边界风险，属于不同维度，不能共用或混淆为一个状态。发起人应能推动核实和发布结果，但不能替成员完成确认。

## 2. 证据与设计处理

| 发现 | 证据 | 处理 |
|---|---|---|
| 最终确认有明确价值 | D01–D03 均把“发布不是考虑中”视为流程核心 | 保留发起人明确勾选与发布节点；增加成员收到结果后的回执说明。 |
| 日常语言优于硬／软术语 | D01、D03 认为“没有这个我就来不了 / 有更好，没有也行”直观 | 保留日常语言，不向用户暴露“硬／软约束”术语。 |
| “待核实”与“边界风险”需前置且分开定义 | D01、D03 在中后段才区分两者；D02 需要明确风险是否阻断发布 | 条件页同时定义两者：待核实是未验证，边界风险是已验证但无余量；后者不阻断发布，但要求发起人知情确认。 |
| 邀请进度不能与条件可信度混用 | D03 将“待核实”理解为成员尚未回复 | 后续状态模型拆为“等待回复 / 已反馈”和“待核实 / 已确认 / 边界风险”。本轮原型先明确文案边界。 |
| 发起人不能替成员确认 | D02 明确指出责任边界；D03 也关注成员是否有后续确认机会 | 将演示按钮改为“收到成员本人确认”；文案明确成员自行更新，发起人只能记录回执。 |
| 风险需要解释行动预期 | D01、D02 寻找边界风险的“处理”入口；D03 希望知道后续动作 | 明确边界风险无需被消除；增加暂定、改选、接受缺席的低保真操作反馈。 |
| 状态变化需同步可见 | D03 发现核实后表格仍显示待核实 | 修复原型：成员本人确认后，网格即时更新为“已确认”。 |
| 参与规则与关键成员定义不清 | D01、D03 均追问人数是否包含发起人、关键成员如何指定 | 在规则下方增加即时说明；后续测试关键成员指定机制与其社交接受度。 |
| 信息一致性影响信任 | D01 发现候选数量与列表不一致 | 修复为“4 个已有候选”。 |

## 3. 仍待验证的假设

1. 成员会不会因不想拖慢群体而把“待核实”误报为偏好或确认；仅靠提示是否足够。
2. “关键成员必须确认”是否会造成被分级或被点名的社交不适，何种命名和设置方式可接受。
3. 发起人看到聚合冲突类型但看不到个人理由时，是否仍能有效推进协调。
4. 发布后的成员回执是增强确认感，还是为低重要度聚会增加负担。
5. 边界风险在整个流程中以一致视觉提示呈现，是否能被快速理解且不会被误认为阻断状态。

## 4. 本轮原型修订

- 修复候选数量不一致与核实后状态表未更新的缺陷。
- 在第 1 步补充参与规则、发起人是否计入人数、关键成员的定义。
- 在第 2 步前置边界风险，并说明邀请回复与条件待核实是不同信息。
- 在第 3、4 步同时显示“待核实”和“边界风险”，说明后者不阻断发布且无需被消除。
- 将确认按钮改为“收到成员本人确认”，并加入暂定、改选和接受缺席的交互反馈。
- 在发布页说明成员会收到结果回执。

## 5. 下一步

以修订后的原型进行一次针对性回测，优先邀请 2–3 名未参与首轮的目标用户。任务重点不是增加新功能，而是验证：状态是否可在不读长说明的情况下被区分、发起人是否理解责任边界、以及边界风险和成员回执是否造成额外负担。
