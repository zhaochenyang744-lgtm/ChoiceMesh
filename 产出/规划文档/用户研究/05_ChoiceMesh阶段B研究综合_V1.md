## 1. 结论

ChoiceMesh 要解决的问题真实且重复出现：群聊可以发起讨论，却难以把分散、含条件、会变化的信息变成可确认的共同决定。三位发起人都承担了人工追问、整理、比较、私聊核实与最终定案；三位参与者都观察到或经历了信息不完整、沉默者、临时变化或为了不扫兴而模糊表达的情况。

研究建议进入阶段 C，但不宜直接进入完整开发。下一轮须以行为任务验证：成员是否愿意在低摩擦入口中提交结构化条件、自然语言能否稳定表达“不能参加”和“更希望”、以及推荐解释能否既有用又不造成社交压力。

## 2. 核心发现

### 2.1 群聊的缺口在“整合与确认”，不是缺少讨论

六位受访者都以现有群聊为主要协调场所。群聊和投票在收集两三个明确选项的倾向时足够快，但无法可靠处理以下信息：

- 同一人对不同方案有不同条件；
- “可以”“都行”“可能”不等于确认；
- 时间、预算、交通、最晚离开时间等信息散落在不同消息中；
- 候选方案、人数和场地可用性会在过程中变化。

因此，首要机会不是替代群聊，而是把一次协调中需要反复追问和人工归纳的部分结构化，并把结果带回群聊确认。

### 2.2 发起人的人工协调负担稳定存在

三位发起人均描述了类似工作：先找候选方案，再催回复、逐一核实模糊条件、私下确认敏感或迟到信息、重述选项、联系场地、预订与提醒。参与者也能看见这类“幕后工作”，但通常只承担自己的回复。

这支持将产品的主要价值描述为：减少发起人的信息整合与反复追问，而不是替群体自动作决定。

### 2.3 “硬条件 / 软偏好”有价值，但术语与误判是关键风险

所有受访者都能区分“没有它就无法参加”和“有更好、没有也可接受”的差异；也都举过把模糊语句错当偏好、后来才发现实际无法参加的经历。研究中最常见的误判来自距离、预算、时间和饮食限制的真实强度不明。

设计含义：

- 不应从一句自然语言自动断言条件强度；
- 应让成员用日常语言自选，例如“没有这个我就来不了”和“有更好，没有也行”；
- 把识别出的内容回显给本人确认，再参与计算。

### 2.4 隐私保护不是隐藏结果，而是不公开个人原因

多数人愿意让群体看到聚合后的可行性与取舍，但不希望公开谁预算有限、谁未回复、谁因私事无法参加，或由系统点名造成压力。部分敏感原因可只对发起人可见，群内只看结果与不具名的冲突概览。

设计含义：默认显示“方案满足 / 冲突的条件类别及人数”，不显示个人理由、未回复名单或责任归属；需让发起人确认后才发布最终方案。

### 2.5 “全员一致”并非固定规则，需显式设置参与门槛

低到中等重要度的活动中，许多人接受达到最低人数即可成行；涉及核心人物、难得聚会或高变更成本时，群体更在乎全员或关键成员的可参加性。谁是关键成员、最低人数是多少，应由发起人和群体在活动开始时设定，而不应由系统默认为所有人等权且必须到场。

### 2.6 独立链接有机会，但入口必须低摩擦

受访者普遍偏好留在群聊中，且对外部链接、登录、授权和长表单敏感。愿意尝试的前提是：无需注册、无需读取日历或联系人、移动端几秒可完成、以点选为主、字段只与当前活动相关。访谈只能说明设计条件，不能证明完成率；阶段 C 必须测量实际完成行为。

### 2.7 AI 的合理位置是整理和解释，不是替人表态

受访者接受 AI 将零散回复整理为确认项、找出条件冲突、给出候选比较与简短理由。明确拒绝的边界包括：替成员猜测、把“可能”视为确认、公开敏感原因、自动催促或自动代替发起人定案。

## 3. 假设状态

| 假设 | 阶段 B 状态 | 证据与处理 |
|---|---|---|
| V01 协调成本真实且重复 | 支持 | 6/6 描述了追问、整合、迟迟未确认或条件遗漏；3/3 发起人承担主要整理工作。 |
| V02 普通投票无法处理硬条件 | 支持 | 6/6 提到简单投票或群聊无法表达条件、模糊回复或后续人工确认。 |
| V03 发起人愿意录入候选方案 | 部分支持 | 候选通常由发起人搜集或筛选，但并非所有候选在活动开始时已齐备，且可能替换。保留“现有候选”边界，支持增量添加与替换。 |
| V04 成员愿意填写独立表单 | 有条件支持 | 可接受的条件是一键进入、免注册、短时点选；实际完成率尚未验证。 |
| V05 取舍解释比票数有价值 | 部分支持 | 发起人需要较完整理由；参与者多只需要一句可理解的结果原因。应测试分层解释，而非统一长解释。 |
| V06 需要一轮修订 | 支持 | 候选变化、场地不可用、迟到条件和沉默者在所有案例中出现。 |
| U01 能理解硬/软区分 | 有条件支持 | 概念直观，但原始表达常含糊。用生活化文案并要求确认。 |
| U04 无解可引导继续 | 初步支持 | 受访者希望看到不点名的冲突类别与可行动调整，而非“无解”终止。 |
| F01 默认等权符合预期 | 部分支持 | 偏好宜平等对待，但活动重要性、关键成员和最低人数会改变规则。 |
| F02 硬条件不应被多数偏好覆盖 | 支持 | 各角色均将真实不可参加条件视为先于人数或偏好。 |
| P01 聚合结果足以解释推荐 | 支持 | 可共享聚合可行性与取舍；个人理由默认不公开。 |

## 4. 设计约束与下一步决策

1. 保持“已有候选活动”定位，不将地点发现或自动生成行程纳入 MVP；但允许发起人在协调过程中增量新增、删除或替换候选。
2. 首屏只收集当前决策需要的最小信息：可参加时段、预算上限、最晚离开时间、不可接受项，以及可选偏好。
3. 采用“本人确认 → 系统计算 → 发起人确认发布”的三段式责任边界。AI 仅整理、比较和解释。
4. 结果页采用分层信息：成员默认看到简短建议和不具名理由；发起人可查看更完整的条件覆盖与待确认项。
5. 在建房时设置参与规则：全员、关键成员必须参加，或达到最低人数即可。
6. 进入阶段 C，先测现有群聊/投票的基线过程；该阶段尚不验证 UI 美观，也不等同于产品可用性测试。

## 5. 局限

- 样本量为 6，适合形成设计假设与反证，不可估计总体比例。
- 样本以熟人社交、小型活动为主；约 10 人案例只用于识别规模变化，不作为目标用户的代表。
- 回顾式访谈可能遗漏当时细节；阶段 C 需用实际任务记录时间、追问次数和遗漏情况。
- 对独立链接的接受度是意向而非行为数据，不能以此推断转化率。
