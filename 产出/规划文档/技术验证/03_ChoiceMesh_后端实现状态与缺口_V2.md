## 1. 已具备的基础

`choicemesh-mvp/` 目前已有以下可公开的实现基础：

- Supabase 身份认证、房间、成员、提案、提案支持、私密条件与已发布版本的数据表；
- 基于邀请码的 `join_room` RPC；
- 非提议者支持待审提案、将其原子切换为当前提案的 RPC；
- 只追加的发布版本基础；
- 私密自然语言解析 API、DeepSeek 环境变量配置与输出校验；
- 浏览器语音转写入口，作为私密文本输入的前置步骤。

## 2. 尚未达到 V2 目标契约的项目

| 缺口 | 当前代码状态 | 后续实现要求 |
| --- | --- | --- |
| 完整提案字段 | `proposals` 尚未持久化地点/区域与结束时间；创建 UI 也未要求预计费用 | 增加字段与非空校验；缺任一关键字段不得计算可发布性 |
| 两种参与规则 | 当前仅以 `minimum_confirmations` 建模 | 增加显式 `participation_rule`，并可计算 `everyone_confirmed` |
| 继续决定 | 尚无 `ContinuationDecision` 表或服务端验证 | 达到最低人数但仍有人未确认时，记录已确认成员的明确继续决定 |
| 变更后的再确认 | 支持提案后尚未重置受影响成员状态 | 由服务端识别时间/地点/费用影响范围并标记 `needs_verification` |
| 发布确认记录 | `publish_room` 尚未持久化发布者的显式确认回执 | 将确认记录纳入发布事务与审计日志 |
| 共享查询 | 当前有 `room_summary()` 基础汇总 | 增加 V2 的匿名任务、边界风险与小群体降级规则 |
| 邀请体验 | 当前实现可由邀请码加入，但前端主要生成邀请链接 | 正式产品将邀请码作为主要输入与邀请形式，链接仅可作为便捷封装 |

## 3. 发布解释

GitHub Pages 仅部署静态高保真原型，不连接上述后端。因此公共演示不得被理解为已有真实多成员协作、数据库持久化或隐私权限执行。

后端代码、迁移、AI 提示词和评测文档会随仓库公开，以便后续继续开发与审查；`.env.local`、API 密钥、Supabase 密钥与参与者资料不会公开。

## 4. 后端重新部署前的最低完成条件

1. 完成上表所有 P0 数据与事务规则；
2. 为房间、私密条件、提案支持和发布版本补充端到端测试；
3. 用两个真实测试账号验证 RLS，确保无法读取他人原文、解析结果或精确数值；
4. 对 AI 解析执行离线评测与失败回退测试；
5. 再决定是否将 `choicemesh-mvp` 部署为真实应用。
