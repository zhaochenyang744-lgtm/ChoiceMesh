| 字段 | 内容 |
|---|---|
| 版本 | V1.0 |
| 日期 | 2026-08-06 |
| 状态 | 执行与分析完成；探索性样本 |
| 测试材料 | `产出/交付物/产品原型/02_ChoiceMesh_MVP中保真任务流原型_V1.2/index.html` |
| 原计划样本 | 5–6 名未参与阶段 D 的目标用户 |
| 实际样本 | 4 名文字过程记录 / 文字反馈；其中 M01、M04 提供完整过程，M02、M03 为补充反馈 |

## 1. 目的

验证中保真流程能否让用户在不阅读长说明的情况下：

1. 区分“等待回复”“待核实”“边界风险”；
2. 找到当前卡点，并判断下一步由谁处理；
3. 理解发起人不能替成员确认；
4. 完成从协调、暂定到最终发布的闭环；
5. 理解发布后“仍有问题”会回到协调中，而非覆盖已发布结果。

不测试视觉偏好、真实 AI 质量、登录流程或外部活动数据。

## 2. 参与者

- 5–6 名最近 3 个月参与过 3–6 人活动协调的人；
- 至少 2 名经常发起活动的人；
- 不纳入阶段 D 首轮或修订版测试参与者；
- 不要求提供真实联系人、行程、预算或私人原因；
- 默认不录音。若记录屏幕或录音，须在开始前另行取得明确同意。

## 3. 单场安排

- 时长：25–30 分钟；
- 形式：单人远程或当面测试；
- 原型角色：默认以发起人视图体验；
- 方法：任务执行 + 思考出声 + 简短回访；
- 主持原则：不解释概念、不教操作、不代替参与者判断。

## 4. 统一情境与任务

### 情境

你正在组织四位朋友的周末活动。当前有几个候选活动；一位成员尚未反馈，另一位成员已经反馈但还没有核实交通，另有一项预算正好压线。你希望在不公开私人原因的前提下，判断活动能否正式确认。

### 任务

| 编号 | 给参与者的任务 | 主要观察 |
|---|---|---|
| T1 | 不点击帮助文字，先说出活动现在为什么还不能发布。 | 是否区分等待回复、待核实与边界风险。 |
| T2 | 请推进活动，直到你认为它可以发布。边操作边说出谁需要做什么。 | 能否找到责任人；是否把提醒误作确认。 |
| T3 | 到候选比较页后，说明候选 C 目前的状态，以及预算压线会不会阻止发布。 | 是否理解边界风险。 |
| T4 | 请暂定并发布候选 C。 | 是否理解参与规则、暂定与“我确认”动作。 |
| T5 | 假设成员在发布后提出新问题。请处理它，并说出之前发布的方案会发生什么。 | 是否理解问题回流与版本保留。 |

若参与者停滞超过约 45 秒，可重复任务原话；仍无法继续时，记录为未完成后再演示下一步。不要解释术语含义。

## 5. 主持提纲

### 开场

说明这是流程测试，不测试参与者能力；没有正确答案。请参与者边操作边说出他们看到、理解、犹豫或期待的内容。可跳过任何问题或随时停止。

### 任务后追问

- 哪个状态最容易理解？哪个状态最容易混淆？
- 你是否知道下一步由谁做？
- 哪些信息你愿意提交？哪些信息只愿意让发起人或系统看到？
- 最终发布动作的分量是否合适？
- 整个流程中，哪里最像你真实使用时会卡住的地方？

### 收尾

询问是否还有遗漏的操作、状态或担忧。不要在测试过程中辩护设计或承诺功能。

## 6. 记录指标与判定

| 指标 | 记录方式 | 成功信号 |
|---|---|---|
| T1 状态识别 | 正确 / 部分正确 / 错误；原话 | ≥4/5 不把等待回复、待核实和边界风险混为一类。 |
| T2 责任边界 | 是否让成员本人确认 | ≥4/5 不认为发起人可替成员确认。 |
| T3 风险理解 | 是否认为边界风险阻断发布 | ≥4/5 说明其不阻断但需保留。 |
| T4 发布闭环 | 完成 / 提示后完成 / 未完成；耗时 | ≥4/5 无主持解释即可完成。 |
| T5 问题回流 | 是否知道回到协调中且保留版本 | ≥4/5 正确说明。 |
| 社交压力 | 参与者提到的担忧 | 不出现新的、反复出现的公开点名或强迫披露顾虑。 |

若任一安全关键误解（发起人可替成员确认、待核实可直接发布、硬冲突可被偏好覆盖）在 2 名及以上参与者中出现，则暂停高保真设计，先修订流程与测试。

## 7. 输出

- 每位参与者一份匿名原始记录；
- 任务完成矩阵、问题严重度表与原话摘录；
- 中保真测试综合结论；
- 原型 / 规格修订清单与决定日志。

## 8. 执行偏差

- 实际样本为 4 人，少于原计划的 5–6 人；不得将本轮结果用作通过率或总体比例结论。
- M02、M03 未提供逐项任务耗时和完整操作记录，因此综合分析按“有直接任务证据的参与者数”标注分母。
