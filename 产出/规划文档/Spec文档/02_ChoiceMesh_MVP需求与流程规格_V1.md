## 1. 决策摘要

ChoiceMesh MVP 服务于 **3–6 人、一次周末或单日活动、成员已有候选活动** 的共同决策。任一成员可用已有候选创建房间并增量补充；进入正式比较时维持 3–8 个有效候选。创建者只是房间来源，不形成持续职责或不同页面：创建后，所有成员使用同一套工作区共同推进决定。它不发现地点、不预订、不替成员判断或确认；它将群聊中分散的条件变成可核实、可比较、可发布的共同决定。

MVP 的核心闭环是：

`创建活动 → 成员分别反馈 → 系统计算候选状态 → 共同处理待核实或冲突 → 暂定 → 任一成员明确发布 → 成员回执 / 回到协调中`

## 2. 研究到需求的映射

| 研究信号 | MVP 决策 |
|---|---|
| 群聊难以区分“可以考虑”和“正式确认” | 成员回复、条件验证、最终发布分为独立状态。 |
| 未核实通勤被隐性共识掩盖 | 待核实条件不得参与“已确认”计算，也不得自动升级。 |
| 压线预算会影响可行性但不必阻断活动 | 将边界风险作为已验证、需知情保留的状态。 |
| 单一发起人承担整理、追问、比较和定案会形成负担 | 创建者只记录房间来源；所有成员在同一工作区查看聚合状态、推进候选并完成明确发布。 |
| 个人原因不愿在群内公开 | 默认向群体显示聚合状态和条件类别，不显示个人原因或未回复名单。 |
| 全员参与不是固定规则 | 创建活动时显式设置最低人数、全员确认或关键成员必须确认。 |
| 用户接受 AI 整理与解释，拒绝 AI 代为决定 | 规则引擎计算状态；AI 只负责提取、澄清和说明，所有提取需本人确认。 |

## 3. 范围

### 3.1 MVP 包含

- 任一成员创建一个 3–6 人的决策房间，录入或增量维护候选；进入正式比较前保留 3–8 个有效候选；创建行为不授予长期协调义务；
- 成员通过低摩擦链接进入，不要求注册、日历或联系人授权；
- 成员为自己填写可参加性、预算、最晚离开时间、不可接受项和可选偏好；
- 规则引擎显示候选的硬冲突、待核实、边界风险、偏好让步与下一步责任；
- 任一成员可暂定、改选、按既定参与规则接受缺席或完成明确发布；
- 发布后成员可回执“收到”或“仍有问题”；后者将房间返回协调中；
- AI 将自然语言整理为结构化候选字段和简短解释，但不改写为已确认事实。

### 3.2 MVP 不包含

- 地点、活动、路线、价格、营业时间或行程发现；
- 自动预订、付款、群聊机器人、日历读写或联系人同步；
- 公开展示个人预算、健康、具体出行或私人原因；
- 多轮无限协商、算法自动定案、成员权重自动推断；
- 跨城市、多日旅行、超过 6 人的大型活动。

## 4. 角色与责任

| 角色 | 可以做什么 | 不能做什么 |
|---|---|---|
| 创建者 | 创建房间、录入初始候选和参与规则 | 获得持续的特殊权限或不同页面；代替成员填写条件 |
| 成员（全体共用同一工作区） | 查看聚合摘要、发送私密提醒、暂定 / 改选 / 接受缺席、完成明确发布；填写和确认自己的条件 | 修改或确认他人条件、查看默认隐藏的私人原因、以沉默代替确认 |
| 规则引擎 | 根据已确认结构化数据计算可行性、冲突、风险与规则门槛 | 推断个人意愿、用偏好覆盖硬条件 |
| AI | 提取候选字段、提出澄清、生成结果说明 | 确认事实、改变状态、排序替代规则、发布方案 |

## 5. 核心状态模型

### 5.1 成员回复状态

这条状态描述成员是否已参与，而非某个条件是否可行。

| 状态 | 定义 | 下一步责任 | 群体可见 |
|---|---|---|---|
| 等待回复 | 成员尚未提交任何反馈 | 该成员；任何成员可发送一次私密提醒 | 仅聚合人数，例如“2/4 已反馈” |
| 已反馈 | 成员已填写，存在待核实或待确认条件 | 对应成员 | 聚合人数 |
| 已确认 | 成员已确认最终候选的必要条件与参加意愿 | 无 | 聚合人数 |
| 无法参加 | 成员明确无法参加某个候选或本次活动 | 全体决定改选、调整或按规则接受缺席 | 条件类别与人数，不显示私人原因 |

### 5.2 条件状态

这条状态描述已反馈信息的可靠性与强度。

| 状态 | 定义 | 计算规则 | 视觉要求 |
|---|---|---|---|
| 待核实 | 成员已提交反馈，但条件尚未被本人验证，例如“应该可以” | 不能作为已确认，阻止依赖它的最终发布 | 与“等待回复”使用不同图标、标题和行动语言；显示“已回复，待本人验证” |
| 已验证 | 成员确认具体条件可满足 | 可参与硬条件计算 | 绿色 |
| 硬冲突 | 已验证条件与候选不兼容 | 该候选对该成员不可行；不得被偏好抵消 | 红色 |
| 边界风险 | 已验证但无余量，例如预算正好到上限 | 不阻止发布；成员确认该风险会被保留，发布时仍须保留 | 琥珀色虚线 |
| 偏好让步 | 非阻挡偏好未满足 | 不影响可行性；保留在解释中 | 中性灰色 |

### 5.3 房间状态

`草稿 → 收集反馈 → 协调中 → 暂定方案 → 已发布`

- 发生新问题、候选变化或成员提出“仍有问题”时，房间返回 **协调中**；保留之前发布记录与原因。
- 只有满足参与规则、没有依赖未核实条件、且任一成员完成发布确认时，才可从 **暂定方案** 进入 **已发布**。

## 6. 参与规则与计算规则

### 6.1 创建时必填

创建者从以下规则中选择一种，并看到即时解释：

1. **最低人数成行**：已确认成员计入人数；达到设定人数并满足该组成员的硬条件即可发布。
2. **全员确认**：所有受邀成员都需确认最终候选。
3. **关键成员必须确认**：发起人显式指定关键成员；该设置只定义活动是否能照常进行，不代表成员价值高低。

### 6.2 候选计算顺序

1. 排除已确认硬冲突的候选；
2. 标识影响发布的待核实条件与责任人；
3. 判断是否满足参与规则；
4. 标识边界风险与偏好让步；
5. 输出候选状态及原因，不自动宣布胜出方案。

候选只可被标为以下之一：

- **不可行**：存在不能被当前参与规则接受的硬冲突；
- **可推进，待处理**：无硬冲突，但有待核实条件或未满足的参与规则；
- **可发布，有风险**：满足发布门槛，但存在边界风险或偏好让步；
- **可发布**：满足发布门槛，且无未处理风险。

## 7. 页面与关键字段

| 页面 | 主要用户 | MVP 内容 | 完成条件 |
|---|---|---|---|
| 创建活动 | 任一成员 | 标题、日期范围、至少 1 个已有候选、参与规则、最低人数 / 关键成员 | 房间进入收集反馈；正式比较前补足 3–8 个有效候选 |
| 成员反馈 | 成员 | 每个候选的可参加性；时间、预算、最晚离开、不可接受项、偏好；隐私选择 | 成员主动提交，系统回显提取结果 |
| 候选比较 | 全体 | 每个候选的可行性、已反馈人数、下一步责任、聚合冲突 / 风险 / 让步 | 任一成员可暂定或返回调整 |
| 协调与修订 | 全体 | 私密提醒、候选增删、待核实回执、暂定 / 改选 / 接受缺席 | 无待核实依赖且满足参与规则 |
| 最终确认 | 全体 | 参与规则检查、实际确认人数、最低门槛、保留风险、发布声明 | 任一成员勾选“我确认”后发布 |
| 已发布与回执 | 全体 | 最终方案、行动摘要、风险 / 让步、成员“收到 / 仍有问题” | 所有回执记录；新问题回到协调中 |

## 8. 隐私与数据规则

- 默认不显示成员的私人理由、预算数字、精确出发位置或未回复名单。
- 成员可选择将原因保持仅自己可见，或只向群体显示不带归属的聚合类别；MVP 不设置创建者专属的原因查看权限。
- 群体默认看到“有 1 项交通待核实”“有 1 项预算边界风险”这类聚合信息；不显示归属。
- 当有效参与人数少于 4 人，默认将可反推归属的风险类别降精度为“存在已验证风险”；成员可在自己的条件中选择是否允许显示类别，但仍不显示归属、具体数值或原因。
- 房间链接采用不可猜测的访问令牌；成员只可读取本房间数据；无注册不等于无权限控制。
- “共同工作区”接口只返回聚合字段，不返回成员姓名、条件归属、私人原因、路线、预算数字或未回复名单；前端隐藏不是权限控制。
- “我的条件”由受邀链接绑定的成员身份确定。服务端必须验证该身份，且只返回、写入该成员自己的原始条件；不提供前端切换成员的入口。
- 创建者不获得额外的数据读取范围。篡改成员 ID、页面路径或请求参数以读取/修改他人原始条件时，服务端必须拒绝并且不得在响应中返回这些字段。
- MVP 不收集健康、身份、联系人、日历和支付信息。
- 任一成员发送提醒时，系统只提醒状态，不自动催促、超时判定或披露他人原因。
- 提醒以收件成员为单位显示已发送与冷却状态；冷却期间不得重复发送。提醒不改变“等待回复”“待核实”或确认计数。

## 9. AI 与规则引擎边界

### 9.1 AI 输入与输出

- 输入：成员主动提交的短文本或点选信息。
- 输出：提取出的字段草稿、缺失项提示、面向成员的确认问题、基于规则结果的简短说明。
- 确认：任何 AI 提取字段必须由该成员确认后，才写入计算状态。

### 9.2 规则引擎必须确定性处理

- 时间重叠、预算上限、容量、最低人数、关键成员、硬冲突、待核实阻断与发布门槛；
- 规则输出必须可复现，并可追溯到成员确认的结构化字段；
- AI 调用失败时，仍可显示已确认字段、规则计算结果和模板化说明。

## 10. MVP 验收标准

| 编号 | 验收标准 |
|---|---|
| AC01 | 成员可以在不注册的情况下完成一次最小反馈；不要求日历或联系人授权。 |
| AC02 | 系统将“等待回复”与“待核实”分别显示，且二者不会互相自动转换。 |
| AC03 | 待核实条件不能被计为已确认，也不能支持最终发布。 |
| AC04 | 边界风险以不同于待核实的视觉与文案呈现，并在发布后保留。 |
| AC05 | 任一已确认硬冲突不得被多数偏好覆盖。 |
| AC06 | 任何成员都无法编辑或确认他人的私人条件；只能看到成员本人提交的聚合回执。 |
| AC07 | 比较页对每个可推进候选显示“下一步由谁处理”的聚合行动提示。 |
| AC08 | 暂定、改选和接受缺席都会改变房间状态，并留下可见记录。 |
| AC09 | 发布要求满足参与规则、无依赖待核实条件，并由任一成员完成“我确认”动作。 |
| AC10 | 成员可在发布后提交“仍有问题”，房间回到协调中但保留已发布版本。 |
| AC11 | AI 提取未经成员确认时不得进入规则计算。 |
| AC12 | 群体视图不得显示默认隐藏的个人原因或未回复名单。 |
| AC13 | 共同工作区的接口仅返回聚合状态；创建者和任一成员均不能通过客户端参数读取或改写他人的原始条件。 |
| AC14 | “等待回复”与“待核实”必须同时以不同图标、不同状态文案和不同下一步行动呈现，不能仅靠颜色区分。 |
| AC15 | 成员可自行选择并保存预计确认时间；该状态不计为确认、不自动转为缺席，群体只见匿名的“已有预计时间”。 |
| AC16 | 有效参与人数少于 4 人时，群体视图对可能反推归属的边界风险默认隐藏类别，仅显示“存在已验证风险”。 |
| AC17 | 私密提醒显示“已提醒”与冷却状态，不能替成员提交反馈或改变任何计算状态。 |

## 11. 首个可用版本的度量与后续验证

以下指标不是当前已证实的目标，而是开发后需要测量的验证项：

- 成员进入链接后完成最小反馈的比例与中位时长；
- 从创建到首次暂定、从暂定到发布的耗时；
- 每次活动的待核实数量、提醒数量和回到协调中的次数；
- 发布时仍存在的边界风险与偏好让步数量；
- 成员是否能在不看帮助文案时区分等待回复、待核实与边界风险；
- 用户是否认为聚合解释减少了追问，同时没有增加社交压力。
