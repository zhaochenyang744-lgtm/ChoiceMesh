## 1. 问题

朋友、同学或同事约活动时，真正拖慢决定的往往不是“没有想法”，而是：

- “应该可以”“再看看”被误当作已经确认；
- 时间、通勤、预算等私人条件不愿在群聊中展开；
- 一个提案被改变后，谁需要重新确认并不清楚；
- 发布后的异议容易让已做出的决定被悄悄推翻。

## 2. 产品定位

ChoiceMesh 是一个小组活动的共同决策工具，不是地点搜索、投票器或 AI 活动推荐器。

它围绕一个当前提案，帮助群体回答：

1. 这个提案是什么；
2. 还缺谁的本人确认；
3. 是否已满足既定参与规则；
4. 现在发布是否意味着正式决定。

## 3. 当前目标用户与场景

- 3–6 人的小型朋友、同学或同事活动；
- 创建时已有一个活动想法，而非从地点库里挑选；
- 成员愿意私下表达可参加性、通勤或预算边界；
- 群体需要从“讨论中”进入可追溯的正式结果。

## 4. V2 核心主张

> 不同成员可以保留不同条件，但群体需要一个清楚、可核实、不会被沉默误读的共同结果。

## 5. V2 产品边界

### 包含

- 一个完整的当前提案：活动、时间、地点/区域、预计费用；
- 邀请码加入房间；
- 成员以文字或语音转写表达自己的条件；
- AI 生成仅本人可见的条件草稿，成员编辑并确认；
- 匿名汇总的进度、阻塞项和边界风险；
- 成员提出提案变更或替代提案，并由另一成员支持；
- 显式发布与可追溯的已发布版本。

### 不包含

- AI 自动推荐活动、地点或行程；
- AI 代替成员确认、拒绝、催促或发布；
- 公开成员原文、精确路线、私人原因或个人预算；
- 自动把沉默、提醒发送、截止时间到达解释为确认或缺席；
- 自动预订、支付或日历写入。

## 6. 首次 GitHub 发布范围

GitHub Pages 只部署可交互的高保真原型，用于展示产品主流程；不部署真实数据库、鉴权或 DeepSeek 密钥。

仓库同时公开后端基础代码、数据库迁移、AI 提示词和评测规范，但环境变量与真实密钥仅保留在本地或部署平台。
