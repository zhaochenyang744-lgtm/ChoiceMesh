## 1. MVP 要验证的命题

> 当 3–6 人需要从已知候选活动中做决定时，把每个人的硬性约束与软性偏好结构化，并提供可解释的方案排序，是否能比群聊追问或简单投票更快形成可接受的共同方案？

## 2. MVP 首发任务

在同一城市中，从 3–8 个候选周末活动里选择一个共同方案。

候选方案由发起人提供，包含：

- 名称；
- 日期与时间；
- 地点或区域；
- 预计人均费用；
- 活动类型；
- 可选备注或链接。

这一设计避免 MVP 依赖实时地点数据库，也避免 AI 编造价格、营业时间和可用性。

## 3. 用户角色

### 发起人

- 创建决策房间；
- 添加候选方案；
- 设置提交截止时间；
- 分享邀请链接；
- 查看整体进度；
- 发起一轮修订；
- 关闭或确认最终方案。

### 成员

- 通过链接加入；
- 填写显示名称；
- 对时间、费用、距离和活动类型表达约束与偏好；
- 查看推荐和取舍；
- 提交接受、保留意见或不可接受；
- 确认最终方案。

## 4. P0 功能

### 4.1 创建决策房间

- 输入活动标题和简短背景；
- 添加 3–8 个候选方案；
- 设置 3–6 人的目标成员数；
- 生成可分享链接和房间码。

### 4.2 成员加入与进度

- 无需注册即可加入；
- 使用房间内唯一显示名称；
- 显示已提交人数，不公开未授权的具体偏好；
- 允许在截止前修改自己的输入。

### 4.3 约束与偏好收集

结构化字段：

- 可参加时间；
- 最高预算；
- 可接受区域或最长通勤时间；
- 活动类型偏好；
- 无障碍、饮食或其他必要条件；
- 自由文本补充。

每项必须区分：

- `必须满足`；
- `最好满足`；
- `不在意`。

### 4.4 自然语言辅助

成员可选输入一句自然语言，例如：

> 周六下午都可以，最好别超过 40 澳元，我不太想走太远。

AI 将其解析为结构化建议，但必须由用户检查并确认后才能保存。

### 4.5 可行性检查

- 硬性约束不满足的候选方案标记为不可行；
- 显示失败原因类别和受影响人数；
- 默认不向其他成员公开敏感的个人原因；
- 若所有方案都不可行，进入“无解”状态。

### 4.6 方案排序

对可行候选方案按透明规则计算：

1. 硬性约束通过；
2. 满足软性偏好的比例；
3. 成员满意度的最低值；
4. 总体满意度；
5. 并列时使用稳定、公开的排序规则。

### 4.7 AI 取舍说明

每个推荐卡片包含：

- 为什么可行；
- 满足了哪些共同偏好；
- 主要取舍；
- 仍有保留意见的人数；
- 计算依据的展开入口。

### 4.8 反馈与一次修订

成员对推荐选择：

- 可以接受；
- 可以接受，但有保留意见；
- 不可接受，并选择原因。

系统总结反馈，允许发起人修改候选方案或请成员放宽一项条件，然后重新计算一次。

### 4.9 最终确认

- 展示最终候选方案；
- 每位成员独立确认；
- 全员确认后生成行动摘要；
- 未全员确认时不得显示“已经决定”。

### 4.10 基础评测与日志

- 保存匿名化输入、规则结果、AI 输出和版本号；
- 记录解析失败、无解、解释与计算不一致等错误；
- 支持运行固定测试样例；
- 不在日志中保存 API 密钥或无关个人信息。

## 5. P1 功能

- 两轮以上的修订历史；
- 成员之间的匿名条件协商；
- 候选方案模板；
- 日历文件导出；
- 决策结束后的满意度回访；
- 更完整的房间管理与身份验证。

## 6. 明确不做

- 不接入私人日历；
- 不读取群聊消息；
- 不自动搜索地点、航班或酒店；
- 不进行预订和支付；
- 不处理大型组织或正式治理投票；
- 不允许 AI 自动改变成员输入；
- 不用多数票覆盖任何成员的硬性限制；
- 不承诺找到所有人都最喜欢的“最优解”；
- 不在 MVP 中支持超过一次修订。

## 7. 核心状态

```text
草稿
→ 等待成员提交
→ 信息完整性检查
→ 计算中
→ 有可行方案 / 无解
→ 成员反馈
→ 一次修订
→ 最终确认
→ 已完成
```

## 8. MVP 完成标准

- 一个新用户可以独立创建房间并添加候选方案；
- 3 个以上模拟成员可通过独立链接完成输入；
- 可行性结果与人工标注一致；
- 至少能稳定处理“多个可行方案”“仅一个可行方案”“全部不可行”三类样例；
- AI 提取必须经过用户确认；
- AI 解释不得与规则结果冲突；
- 最终状态明确区分“推荐”和“已确认”；
- 项目可以按照 README 在本地启动；
- 固定评测集能够一键运行并输出结果。
