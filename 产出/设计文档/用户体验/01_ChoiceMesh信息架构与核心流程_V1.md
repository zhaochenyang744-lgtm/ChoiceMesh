## 1. 体验目标

用户在任何时刻都能回答三个问题：

1. 现在需要我做什么？
2. 系统为什么得到这个结果？
3. 这只是推荐，还是已经被所有人确认？

## 2. 信息架构

```text
首页
├─ 创建决策
└─ 加入决策

发起人流程
├─ 基础设置
├─ 候选方案
├─ 邀请与进度
├─ 推荐结果
├─ 反馈汇总
├─ 修订
└─ 最终确认

成员流程
├─ 加入说明
├─ 约束与偏好
├─ AI 解析确认
├─ 推荐结果
├─ 反馈
└─ 最终确认
```

## 3. 发起人主流程

```text
进入首页
→ 创建房间
→ 添加 3–8 个候选活动
→ 检查信息完整性
→ 生成邀请链接
→ 等待成员提交
→ 触发计算
→ 查看推荐或无解
→ 收集成员反馈
→ 修改候选或请求放宽条件
→ 重新计算一次
→ 发起最终确认
→ 输出行动摘要
```

## 4. 成员主流程

```text
打开邀请链接
→ 阅读用途与隐私说明
→ 输入显示名称
→ 查看候选方案
→ 填写硬性约束与软性偏好
→ 可选：自然语言补充
→ 检查 AI 解析结果
→ 确认提交
→ 查看推荐与取舍
→ 选择接受/有保留/不可接受
→ 查看修订结果
→ 最终确认
```

## 5. 无解流程

```text
所有候选均违反至少一项硬性约束
→ 明确显示“目前没有可行方案”
→ 按类别展示冲突，不公开敏感原因
→ 给出三类下一步：
   1. 发起人新增或修改候选
   2. 成员自愿调整一项条件
   3. 结束当前决策
→ 重新计算
```

无解页面不得：

- 隐藏冲突；
- 自动放宽成员限制；
- 推荐被规则判定为不可行的方案；
- 使用“最佳选择”措辞。

## 6. 推荐卡片结构

每张卡片按以下顺序呈现：

1. 候选方案名称与关键信息；
2. 可行状态；
3. 推荐位置；
4. 共同优势；
5. 主要取舍；
6. 保留意见人数；
7. 展开查看计算依据；
8. 反馈操作。

## 7. 关键文案原则

- 使用“推荐”“可行”“待确认”，不使用“AI 已决定”；
- 使用“有 1 位成员的预算条件不满足”，不暴露其具体身份；
- 使用“目前没有可行方案”，不使用“你们无法达成一致”；
- 使用“请检查 AI 识别的内容”，不暗示解析一定正确；
- 全员确认前始终显示成员状态。

## 8. 低保真测试任务

### 任务 A：提交约束

参与者根据给定角色卡完成输入，并解释哪些是硬性条件。

### 任务 B：理解推荐

参与者查看三个方案，说明第一名为什么领先、有什么取舍。

### 任务 C：处理无解

参与者在所有候选不可行时选择下一步。

### 任务 D：区分推荐和确认

参与者判断当前是否已经形成最终决定。

## 9. 可用性成功门槛

- ≥80% 参与者正确区分硬性与软性；
- ≥80% 能解释推荐的主要依据；
- 100% 知道 AI 解析需要确认；
- 100% 知道推荐不等于最终决定；
- ≥80% 在无解状态下找到可继续的操作；
- 成员提交中位用时不超过 2 分钟。

## 10. 暂不定义

以下内容等待研究后再进入视觉设计：

- 动效；
- 复杂数据图表；
- 桌面端宽屏布局；
- 自定义公平策略；
- 多轮协商视图。
