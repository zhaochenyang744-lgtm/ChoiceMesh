# ChoiceMesh 文档命名与版本规则

| 字段 | 内容 |
|---|---|
| 版本 | V2 |
| 更新 | 2026-08-19 |

## 1. 命名格式

```text
序号_ChoiceMesh_主题_版本.md
```

- 序号两位，**在同一目录内唯一**，表示阅读顺序而非创建顺序
- `ChoiceMesh` 后**始终**有下划线
- 主题不含空格

示例：

```text
01_ChoiceMesh_项目Brief_V2.md
03_ChoiceMesh_产品需求文档_PRD_V2.md
```

## 2. 版本规则

- `V1`：首个可评审基线
- `V1.1`：不改变核心范围的小幅修订
- `V2`：研究或验证导致的核心范围变化
- **新版本沿用原序号**，旧文件移入同目录下的 `历史版本/` 并去掉序号：
  `01_ChoiceMesh_项目Brief_V1.md` → `历史版本/ChoiceMesh_项目Brief_V1.md`
- 历史版本不删除、不改写；序号只服务于当前生效的那一份
- 只有经过评测并可演示的版本才能进入 `交付物/`

## 3. AI 相关文档单独成类

AI 文档放在 `产出/规划文档/AI工程/`，不混在 Spec 或技术验证里。

理由：它们的变更由**模型或提示词版本**触发，与产品迭代节奏不同步。换模型、改提示词都要动这批文档，而产品范围可能一个字没变。

## 4. 提示词版本必须与代码对齐

提示词契约文档的版本后缀，写**提示词版本号**，不写 `V1`：

```text
03_ChoiceMesh_AI提示词与输出契约_parse-details-v1.md
```

这个 `parse-details-v1` 必须与三处一致：

1. 代码常量 `PARSE_DETAILS_PROMPT_VERSION`
2. 每次调用写入的日志字段 `prompt_version`
3. 评测报告文件名里的版本段

这样从一条线上日志可以直接追到"当时生效的是哪一份契约"。提示词改了就是 `parse-details-v2`，四处同步更新，旧文档进 `历史版本/`。

## 5. 会重复产生的产物用日期，不用版本号

评测报告、事故记录、模型变更记录这类东西，每次产生都是一份独立记录，**历史之间的对比本身就是证据**。用 `V1/V2` 会诱导覆盖，用日期不会。

```text
产出/规划文档/AI工程/评测报告/ChoiceMesh_AI评测报告_parse-details-v1_20260819.md
产出/规划文档/AI工程/评测报告/ChoiceMesh_AI评测报告_parse-details-v2_20260826.md
```

旧报告永不覆盖、永不删除。

阶段记录同理：

```text
M1_问题验证完成记录_20260815.md
```

## 6. 状态标签

每份核心文档应注明以下状态之一：

- `草案`
- `待验证`
- `已评审`
- `执行中`
- `已完成`
- `已淘汰`

## 7. 决策记录

影响用户、范围、AI 行为、指标或技术路线的决定，需要记录：

1. 决策内容
2. 支持证据
3. 被放弃的替代方案
4. 风险与后续验证
5. 决策日期

AI 相关的决策额外记录：**这个决定影响哪个提示词版本、是否需要重跑评测**。
